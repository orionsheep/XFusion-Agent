# XFusion Agent 产品需求文档（PRD）

版本：v0.2  
状态：草案（全量交付版）

## 1. 文档目的

本文档用于定义 `XFusion Agent` 的产品目标、目标用户、核心场景、功能范围、系统边界、关键约束、交付节奏和验收标准。

本产品面向两类目标同时设计：

- `Hackathon 交付目标`：满足超聚变 `AI Hackathon 2026 - 操作系统智能代理` 赛题要求，并在功能、安全、连续任务、交互体验上具备竞争力。
- `平台化演进目标`：从单机智能代理扩展为面向多服务器、多环境、多服务的 AI 运维控制平面。

## 2. 产品概述

`XFusion Agent` 是一个面向 Linux 服务器管理场景的 AI Web 平台。用户通过自然语言下达运维意图，平台基于 `Claude Agent SDK` 进行意图理解、任务拆解和工具调用，并对多台服务器进行安全、可解释、可审计的管理操作。

产品核心能力包括：

- 接入多台 Linux 服务器
- 自动识别服务器环境和已部署服务
- 生成统一 Dashboard 展示系统状态与服务状态
- 通过 AI 对话完成基础运维与连续任务处理
- 对高风险操作进行识别、解释、拦截和审批
- 保留审计链路，支持复盘和演示验证

## 3. 背景与问题定义

### 3.1 当前痛点

当前主流服务器运维仍高度依赖 CLI，存在以下问题：

- 学习门槛高，命令记忆成本高
- 不同发行版和环境的操作路径差异大
- 多服务器场景下的状态感知和管理分散
- 传统面板通常偏“静态管理”，缺少自然语言意图驱动和连续任务闭环
- 直接赋予 AI Shell 能力存在极高安全风险

### 3.2 核心机会

随着 Claude Agent SDK、MCP、策略引擎和可视化监控能力成熟，可以将服务器管理从“命令输入”提升为“意图表达 + 结构化执行 + 风险闭环”。

`XFusion Agent` 的机会不在于做一个聊天框，而在于构建一个：

- 面向服务器管理的 `AI 控制平面`
- 带风控与审批的 `运维行动系统`
- 带多主机状态聚合的 `观察与执行中枢`

## 4. 产品目标

本项目按 `V1.0 全量交付` 定义范围，不采用“先精简版、后完整版”的对外策略。

### 4.1 V1.0 交付目标

一次性交付一个完整可演示、可扩展、可审计的 AI 运维平台，至少包含：

- Web 控制平面
- Claude Agent SDK 中央编排层
- SSH 与 Node Agent 双通道接入
- 多主机 Dashboard
- 自动环境识别
- 自动服务发现
- 自然语言运维操作
- 连续任务处理
- 风险识别、审批与审计

### 4.2 竞赛目标

确保作品在赛题的关键得分项上具备完整闭环：

- 基础需求执行
- 高风险识别与处置
- 环境感知与持续状态更新
- 连续任务处理
- 清晰反馈与行为解释
- 去命令行化交互体验

### 4.3 平台化目标

确保 V1.0 不是一次性 Demo，而是后续可持续演进的系统底座：

- 能稳定管理多台异构 Linux 主机
- 能持续接入新增工具和新增节点
- 能支撑更多主机、更多服务、更多任务类型
- 能深度适配 openEuler 生态和智能运维能力

## 5. 非目标

以下内容不属于当前阶段核心目标：

- 替代 Kubernetes / 云厂商控制台的完整能力
- 支持所有操作系统，仅聚焦 Linux 服务器
- 完整 CMDB / ITSM / 工单系统
- 复杂企业多租户结算能力
- 无边界的自治式 AI 运维

## 6. 目标用户与角色

### 6.1 目标用户

- 参赛评委：关注真实可运行性、完整闭环、安全性、创新性
- 运维工程师：关注批量接入、状态可视化、执行效率、风险可控
- 开发 / SRE：关注服务状态、日志、端口、资源、部署问题定位
- 技术负责人：关注可审计性、权限边界、长期扩展能力

### 6.2 角色定义

- `平台管理员`
  - 管理服务器接入方式、密钥、Agent 安装、策略配置、用户权限
- `运维操作者`
  - 发起查询、执行中低风险操作、查看主机和服务状态
- `审批人`
  - 对高风险动作进行确认或拒绝
- `观察者`
  - 只读访问 Dashboard、日志、审计记录

## 7. 产品原则

- `AI 做理解与编排，不直接拥有生产 root shell`
- `默认安全优先，deny-by-default`
- `所有关键动作必须可解释、可追溯`
- `先结构化能力，后自然语言包装`
- `V1.0 对外范围一次定义完成，内部实施顺序不构成功能裁剪`
- `SSH 与 Node Agent 并存，职责清晰分离`

## 8. 核心产品决策

### 8.1 Agent 技术选型

中央推理层采用 `Claude Agent SDK`。

原因：

- 官方支持会话、权限、MCP、子代理、hooks
- 非常适合做中央编排层，而非每台机器上的自由 Agent
- 能用 in-process MCP tools 快速把业务能力暴露给 Claude

### 8.2 远程执行策略

采用 `混合架构`：

- `P0`: 以 SSH 接入为主
- `P1`: 引入 Node Agent 进行持续采集和结构化执行
- `长期`: SSH 作为兜底和 break-glass 通道保留

### 8.3 控制平面与数据平面分离

- `控制平面`
  - Web UI
  - API 后端
  - Claude Agent Runtime
  - 策略引擎
  - 审批、审计、任务编排
- `数据平面`
  - SSH Connector
  - Node Agent
  - 指标采集器
  - 日志与状态回传

### 8.4 工具调用策略

Claude 不直接调用任意 Bash 管理远端生产环境。

Claude 调用的是平台定义的 MCP 工具，例如：

- `list_hosts`
- `get_host_profile`
- `get_host_metrics`
- `discover_services`
- `inspect_service`
- `run_host_action`
- `search_files`
- `check_port_usage`
- `create_linux_user`
- `delete_linux_user`
- `request_approval`
- `get_audit_trail`

### 8.5 主机选择与任务范围决策

所有涉及执行的任务都必须先完成目标范围决策，再进入工具调用。

- 若用户明确指定主机，则优先使用用户指定范围
- 若用户未指定主机，则系统仅可在用户当前已选主机集或默认工作空间内决策
- 若存在多个可能目标且置信度不足，必须要求用户确认，不能猜测执行
- 批量任务必须显式展示受影响主机列表和数量
- 高风险任务必须展示 `blast radius`，包括主机数、服务数、用户数或路径范围

### 8.6 执行契约

所有执行类工具必须遵循统一结构化契约。

- 输入必须包含：
  - `task_id`
  - `target_host_id`
  - `action_type`
  - `parameters`
  - `risk_level`
  - `dry_run`
  - `timeout_seconds`
- 输出必须包含：
  - `success`
  - `exit_code`
  - `stdout_summary`
  - `stderr_summary`
  - `artifacts`
  - `duration_ms`
  - `retryable`
  - `requires_approval`
- 所有写操作默认要求支持 `dry-run` 或影响预估
- 所有工具都必须返回标准错误码，便于任务恢复和审计
- 执行器必须保证同一 `task_id + action_type + target_host_id` 的幂等识别能力

### 8.7 接入与信任模型

系统必须建立明确的主机和节点信任关系。

- `SSH 接入`
  - 支持私钥认证为主，密码认证仅用于受控环境
  - 首次接入必须校验并记录 host key 指纹
  - 支持凭据轮换和失效处理
- `Node Agent 接入`
  - 采用一次性注册令牌完成 bootstrap
  - 注册后分配唯一 agent identity
  - 控制平面与 Agent 通信必须使用双向认证
  - Agent 重装或身份变更后必须重新注册
- 所有凭据必须加密存储并最小化暴露

## 9. 核心用户场景

### 9.1 基础查询场景

用户输入：

- 查询当前磁盘剩余空间
- 8080 端口被谁占用了
- 查一下 nginx 进程是否正常

系统行为：

- 自动选择目标主机
- 自动识别 OS 与可用工具
- 调用结构化工具执行查询
- 将结果以自然语言和可视化方式返回

### 9.2 多服务器状态场景

用户进入 Dashboard 后，希望看到：

- 所有主机在线状态
- CPU / 内存 / 磁盘 / 负载概览
- 已部署服务与容器摘要
- 异常主机和告警优先级

### 9.3 服务发现与纳管场景

用户把已有服务器导入平台后，希望系统自动识别：

- systemd 服务
- Docker / Podman 容器
- Docker Compose 项目
- 常见 Web 服务与数据库服务
- 监听端口与服务映射关系

### 9.4 连续任务场景

用户输入：

- “帮我排查为什么用户反馈服务起不来”

系统需要：

- 读取服务状态
- 拉取日志
- 识别端口冲突或依赖问题
- 给出原因
- 在涉及 kill / restart 等动作时请求确认
- 执行后反馈结果

### 9.5 高风险场景

用户输入：

- 删除核心目录
- 修改 SSH 配置
- 批量变更用户权限

系统需要：

- 自动识别风险
- 明确说明风险来源
- 触发审批或直接拒绝
- 记录审计信息

## 11. 功能需求

## 11.1 账户与权限

### 11.1.1 功能描述

系统需要提供基础身份认证和角色控制能力。

### 11.1.2 需求项

- 支持本地账号登录
- 支持管理员创建用户
- 支持角色分配
- 支持资源级访问控制
- 支持高风险动作审批人配置

### 11.1.3 P0 验收

- 至少支持管理员和普通操作者两类角色
- 未授权用户无法执行高风险操作

### 11.1.4 权限矩阵

权限必须至少覆盖以下维度：

- 按主机范围授权
- 按环境标签授权
- 按动作类型授权
- 按风险等级授权
- 按页面只读 / 可执行授权
- 审批人与执行人是否允许同一人

建议角色矩阵：

- `平台管理员`
  - 全局配置、主机接入、凭据管理、策略管理
- `运维操作者`
  - 可在授权主机范围内执行 L0-L2 操作
- `审批人`
  - 可审批 L3 操作，但不默认拥有执行配置管理权限
- `观察者`
  - 仅查看 Dashboard、任务记录和脱敏审计内容

## 11.2 主机接入

### 11.2.1 接入模式

- `SSH 模式`
  - 通过主机、端口、用户名、认证方式接入
- `Agent 模式`
  - 在目标服务器安装轻量 Node Agent
- `混合模式`
  - 已安装 Agent 优先使用 Agent
  - Agent 不可用时回退 SSH

### 11.2.2 录入字段

- 主机名称
- 环境标签
- IP / 域名
- SSH 端口
- 用户名
- 认证方式
- 备注
- 风险等级标签

### 11.2.3 认证与接入要求

- SSH 支持：
  - 私钥认证
  - 密码认证
  - Jump Host / Bastion 扩展位
- Agent 接入支持：
  - 注册令牌
  - 节点 identity
  - 心跳状态
  - Agent 版本
- 主机接入后必须保存：
  - host key 指纹
  - 首次验证时间
  - 最近成功连接时间

### 11.2.4 V1.0 验收

- 用户可从 Web UI 手动添加主机
- 系统可完成连接测试
- 系统可保存主机元数据
- 系统可区分 SSH-only、Agent-only、Hybrid 三种状态

## 11.3 环境 Profiling

### 11.3.1 功能描述

主机首次接入后，系统应自动完成环境感知。

### 11.3.2 采集内容

- OS 发行版与版本
- 内核版本
- systemd 状态
- 包管理器类型
- Shell 环境
- Docker / Podman / Compose / K8s 可用性
- CPU、内存、磁盘、网络基础信息

### 11.3.3 输出结果

形成主机画像 `Host Profile`，供：

- Dashboard 展示
- Claude 上下文注入
- 工具路径选择
- 安全策略判断

### 11.3.4 刷新策略

- 首次接入时执行完整 Profiling
- 主机在线期间定期增量刷新
- 环境变化事件触发重新 Profiling
- 任务执行前可按需补采关键字段

### 11.3.5 V1.0 验收

- 至少识别 openEuler / CentOS / Ubuntu
- 能区分 apt / yum / dnf

## 11.4 服务自动发现

### 11.4.1 功能描述

系统对接入主机进行服务扫描，识别已有服务和部署形态。

### 11.4.2 支持发现对象

- systemd services
- Docker containers
- Podman containers
- Docker Compose 项目
- 常见数据库
- 常见 Web 服务
- 监听端口
- 进程与端口映射

### 11.4.3 输出结构

每个服务应包含：

- 服务名称
- 服务类型
- 所属主机
- 状态
- 启动方式
- 端口列表
- 关联进程 / 容器
- 配置路径
- 日志入口
- 发现来源
- 唯一服务键
- 最近发现时间
- 置信度

### 11.4.4 归一化与去重规则

- 同一服务可来自多个发现来源
- 系统需根据端口、进程、容器、unit 名称等规则归并为单一服务对象
- 服务对象必须保留原始发现证据，便于调试和审计
- 对低置信度服务应标记为 `suspected`，而非直接视为已确认服务

### 11.4.5 V1.0 验收

- 用户导入主机后可看到已识别的服务清单
- 至少支持 systemd、Docker、Compose 三类

## 11.5 Dashboard

### 11.5.1 Fleet Dashboard

展示全局资产状态：

- 主机总数
- 在线 / 离线主机数
- 异常主机数
- 平均 CPU / 内存利用率
- 最近高风险操作
- 最近告警
- 服务类型分布

### 11.5.2 Host Dashboard

展示单主机详情：

- 基础信息
- CPU / 内存 / 磁盘 / 网络图表
- 进程摘要
- 端口摘要
- 服务列表
- 最近任务
- 最近日志

### 11.5.3 Service Dashboard

展示服务级状态：

- 服务可用性
- 重启次数
- 日志摘要
- 资源占用
- 配置位置
- 最近变更动作

### 11.5.4 P0 验收

- 至少完成 Fleet Dashboard 和 Host Dashboard

### 11.5.5 数据来源策略

- Fleet 与 Host Dashboard 的实时指标以 Node Agent 为主数据源
- SSH 通道仅用于：
  - 初始接入探测
  - Agent 不可用时的应急快照
  - Break-glass 手工诊断
- Service Dashboard 由服务发现结果、任务结果、日志摘要和实时指标共同组成

## 11.6 AI 对话与任务中心

### 11.6.1 功能描述

用户通过自然语言发起查询和操作，系统将其转换为结构化任务。

### 11.6.2 对话要求

- 支持指定主机和未指定主机两种输入
- 支持多轮上下文
- 支持展示执行计划
- 支持展示工具调用摘要
- 支持返回结构化结果和自然语言总结

### 11.6.3 任务类型

- 查询类任务
- 诊断类任务
- 变更类任务
- 批量类任务
- 需审批任务

### 11.6.4 任务状态

- `queued`
- `running`
- `waiting_approval`
- `succeeded`
- `failed`
- `cancelled`

### 11.6.5 P0 验收

- 支持基础单轮闭环
- 支持至少一个连续任务演示场景

### 11.6.6 会话与恢复模型

- 每个用户会话必须绑定：
  - user_id
  - 当前工作空间
  - 已选主机集
  - 最近任务上下文
  - 审批挂起点
- 审批触发后，任务必须进入 `waiting_approval`
- 审批通过后，系统基于相同会话上下文恢复任务，而非重新规划整个任务
- 长任务页面刷新后必须可恢复查看当前状态

### 11.6.7 目标主机选择规则

- 若用户输入明确主机名，以明确主机为准
- 若用户输入服务名但未指定主机，系统只能在当前工作空间内检索服务归属
- 若匹配结果超过一个，必须要求用户确认
- 对批量主机执行必须显示范围确认卡片

## 11.7 基础系统管理能力

必须覆盖赛题要求的基础操作。

### 11.7.1 磁盘使用情况监测

- 查询整机磁盘空间
- 查询指定分区空间
- 识别高占用目录

### 11.7.2 文件或目录检索

- 按名称查找
- 按路径范围查找
- 按关键字查找

### 11.7.3 进程及端口状态查询

- 查询服务进程
- 查询占用端口的进程
- 查询监听端口列表

### 11.7.4 普通用户创建与删除

- 创建普通账号
- 删除普通账号
- 显示执行影响
- 操作前风险提示

## 11.8 连续任务处理

### 11.8.1 功能描述

支持“观察 -> 推理 -> 修正 -> 再执行”的闭环任务。

### 11.8.2 样例流程

- 查询服务状态
- 拉取日志
- 识别端口冲突
- 查询占用进程
- 请求确认是否结束进程
- 重启服务
- 回收结果

### 11.8.3 要求

- 任务中途失败可返回明确原因
- 支持阶段性输出
- 支持需要人工确认时挂起
- 支持恢复执行

### 11.8.4 任务步骤模型

每个连续任务必须拆解为显式步骤：

- `observe`
- `analyze`
- `plan`
- `approve`
- `act`
- `verify`

每个步骤都必须记录：

- 输入
- 输出
- 工具调用
- 错误状态
- 是否可重试
- 是否可跳过

## 11.9 风险控制与审批

### 11.9.1 风险分级

- `L0`: 只读查询
- `L1`: 低风险写操作
- `L2`: 中风险操作，需要提醒
- `L3`: 高风险操作，需要审批
- `L4`: 禁止操作，系统直接拒绝

### 11.9.2 高风险识别范围

- 删除核心系统文件或目录
- 篡改 SSH / sudo / 防火墙等关键配置
- 大范围用户权限修改
- 批量执行不可逆变更
- 向未知外部地址传输敏感数据

### 11.9.3 审批机制

- 对高风险任务生成审批卡片
- 显示影响范围、风险原因、拟执行动作
- 审批通过后继续执行
- 拒绝后结束任务并记录原因

### 11.9.4 策略输入模型

OPA 或其他策略引擎至少基于以下字段判定：

- actor_id
- actor_role
- target_host_id
- target_host_environment
- target_service
- action_type
- risk_level
- parameters
- path_scope
- blast_radius
- dry_run_result
- time_window
- requires_dual_control

### 11.9.5 V1.0 验收

- 至少实现 `预警 + 二次确认 + 拒绝非法操作`

## 11.10 审计与可解释性

### 11.10.1 记录内容

- 原始用户输入
- 目标主机
- 环境上下文摘要
- Agent 生成的执行计划
- 调用的工具
- 风险等级与策略结果
- 最终执行动作
- 执行输出摘要
- 执行耗时
- 审批信息

### 11.10.2 展示要求

- 用户可查看操作时间线
- 用户可查看被拦截原因
- 用户可查看每一步产生的结果

## 11.11 告警与通知

### 11.11.1 V1.0 范围

### 11.11.2 通知方式

## 11.12 Node Agent

### 11.12.1 职责

Node Agent 不是分布式推理 Agent，而是轻量执行器 / 采集器。

它负责：

- 心跳
- 指标采集
- Host Profile 上报
- 服务发现
- 结构化命令执行
- 日志回传
- 受控文件读取

### 11.12.2 不负责

- 自主决策
- 模型推理
- 自由执行任意高危 shell

### 11.12.3 P1 验收

- Agent 可自动向控制平面注册
- Agent 可稳定回传指标和服务列表
- Agent 可执行受控结构化动作

## 13. 技术方案约束

## 13.1 后端

- 中央后端建议使用 `FastAPI`
- Agent Runtime 使用 `Claude Agent SDK Python`
- MCP 工具优先采用 in-process MCP server

## 13.2 数据存储

- `PostgreSQL`：用户、主机、服务、任务、审计、审批
- `Redis`：任务队列、缓存、短期会话
- `时序库`
  - P0 可先复用 Beszel 或简化存储
  - P1 可接 Prometheus / VictoriaMetrics

## 13.3 安全组件

- `OPA`：策略决策
- 密钥加密存储
- SSH 凭据最小化暴露
- 操作日志留痕

## 13.4 开源复用建议

优先复用以下项目或思路：

- `anthropics/claude-agent-sdk-python`
- `AiondaDotCom/mcp-ssh`
- `open-policy-agent/opa`
- `henrygd/beszel`
- `cockpit-project/cockpit`

## 14. 非功能需求

### 14.1 性能

- 常规查询首屏反馈时间 < 3 秒
- 高风险审批弹出时间 < 2 秒
- 单主机详情页加载时间 < 5 秒

### 14.2 稳定性

- 关键任务失败需明确错误原因
- 网络波动不应导致整个平台崩溃
- 长任务应支持中间状态追踪

### 14.3 安全性

- 默认拒绝未知高风险动作
- 任何危险动作必须有审计记录
- 不允许模型绕过外部策略引擎直接执行

### 14.4 可解释性

- 所有拦截必须给出明确理由
- 所有自动执行必须给出执行摘要

### 14.5 可扩展性

- 能从 SSH-first 演进到 Agent-first
- 能增加新工具而不破坏核心对话层
